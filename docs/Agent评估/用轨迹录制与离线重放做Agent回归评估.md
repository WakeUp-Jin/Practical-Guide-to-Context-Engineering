# 用轨迹录制与离线重放做 Agent 回归评估

> 把一次真实运行存成文件，之后不花钱、不联网地反复重放——让「线上偶发的失败」变成「本地可回归的测试样本」。

## 问题：Agent 的失败现场留不下来

做 Agent 评估时，最容易踩的一个坑是**评估过程本身不可复现**：

- 同一个任务跑两遍，结果不一样。temperature、工具返回、网络抖动、上游限流都会让轨迹分叉；
- 线上出了一次失败，等你回头看，只剩几行日志和一句「刚才它抽风了」，没有当时的 prompt，也没有工具调用的原始返回；
- 想验证「改了 prompt / 换了模型之后有没有退化」，只能重新跑一遍评测集——**每一次验证都要重新烧一遍 token**，跑得越多越心疼，于是大家倾向于少跑，退化就更晚被发现。

前面两篇讲了评估指标和评估器的实现，这一篇补的是另一个环节：**怎么把一次真实运行完整地保存下来，并在之后低成本地反复重放**。

## 思路：把「一次运行」当成测试样本

传统软件里有回归测试，是因为失败可以被保存成一个用例：输入固定、环境固定、断言固定。Agent 之所以难做回归，是因为它的「输入」里混着一次不可控的远程调用。

换个角度想：**如果把 agent 与模型厂商之间的那一段流量完整录下来，这次运行就变成了可存档的样本。**

```
录制阶段（在线，跑一次）
  用户请求 → Agent → [HTTP 代理] → 模型厂商
                        ↓
                 本地 trace（prompt / 工具调用 / 响应 / 原始字节）

重放阶段（离线，跑无数次）
  本地 trace → [重放引擎] → Agent
  （不联系任何厂商，不消耗 token）
```

一次录制，多次重放。重放不再依赖线上环境，也就不再有分叉。

## 录制时要抓住什么

粒度决定了以后能回答什么问题。至少要留下四层：

1. **请求侧的 prompt**（含系统提示词、上下文、工具 schema）——用来回答「它当时到底看到了什么」；
2. **工具调用序列**（名称、参数、返回）——用来回答「失败发生在哪一步」；
3. **模型响应**（含流式分片）——用来区分「模型没输出」和「输出被截断了」；
4. **原始字节**——用来定位编码、截断、SSE 解析这类只在字节层面暴露的问题。

只留 1、2 两层，遇到流式截断就会查不下去；四层都有，才能把失败定位到具体某一步的某个字段。

## 重放的三种用法

### 1. 复现一次失败

线上报错 → 拿到当时的 trace → 本地重放 → 逐步断点。这一步的价值在于**失败从「偶发」变成「必现」**，可以在本地反复单步，而不用在生产环境上赌它会不会再出现。

### 2. diff 两次运行

改了 prompt、改了工具描述、升级了模型版本之后，把新旧两次运行都存下来做 diff：

- 工具调用序列在哪一步分叉？
- 是 prompt 变了导致的第一步分叉，还是模型输出漂移导致的中间分叉？
- token 消耗和步数是变多还是变少？

这比「看两次的成功率数字」能给出多得多的信息。

### 3. 把录像 fork 到另一个模型

同一份 trace 里的用户请求和工具返回是固定的，把它喂给另一个模型重跑，就是一次**受控的 A/B**：只有模型这一个变量在变。这是选型对比时最省钱的做法——不用为了测一个新模型把整个评测集重新跑一遍。

## 与 Eval Harness 的关系

它不是评测集的替代品，而是**评测集的来源之一**：

- 评测集回答「平均而言做得怎么样」；
- 录制重放回答「这一次到底为什么失败，以及修好了没有」。

比较健康的分工是：线上失败 → 录制成 trace → 人工标注失败分类 → 沉淀进回归集 → CI 里每次改动都离线重放一遍。这样「线上偶发问题」就不会过两个月再犯一次。

## 局限

- **重放的是「当时」的那次运行**，不是「所有可能的运行」。它适合做回归和归因，不适合直接拿来算成功率；
- 涉及实时状态的工具（读当前时间、查实时库存）在离线重放时需要显式固定，否则重放会失真；
- 录制的是模型厂商的流量，涉及敏感数据时要注意 trace 的存放位置和脱敏。

## 小结

Agent 评估里最贵的不是跑评测集，而是**为了复现一次失败反复跑评测集**。把一次真实运行录下来存成文件，失败就变成了可存档、可 diff、可回归的样本——这也是把「线上偶发」变成「本地必现」的最短路径。
